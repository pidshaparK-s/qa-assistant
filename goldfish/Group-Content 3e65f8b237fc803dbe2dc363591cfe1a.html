A1: Context

As social.plus becomes an engagement infrastructure built from independently deployable components (Posts, Comments, Reactions, Chat, and others), Groups needs the same treatment. Today, Groups is bundled together with the built-in community construct — membership, roles, and content permissions all live inside one experience. As part of the Componentization initiative, we want Groups to work as an independently configurable component in its own right: a customer should be able to give end users the ability to organize into self-contained groups — with their own membership, join rules, and roles — regardless of which content components (Posts, Comments, Reactions) are attached to those groups, or whether any are.

Componentization principles this supports

  • Groups should be composable. Whatever content components a customer later attaches to a group — Posts, Comments, Reactions — group membership and role configuration should work the same way underneath, through one consistent model.
  • Existing group experiences should continue to work exactly as today (default join behavior, existing roles) — this is a configuration layer on top of current capability, not a rebuild of it.
  • Group-level roles (Community Admin, Moderator, Member, Not a member) reuse the same role already used elsewhere in the product; this doc doesn't introduce a second, Group-specific role system.

A2: MVP Principles & Boundaries

MVP principles

  • Settings are group-specific. A customer can run public groups, private & hidden, private & visible groups side by side, each configured independently.
  • Make permission consequences explicit. Where an existing role (e.g. Moderator) is the mechanism used to approve join requests, the console should make clear what else that role can do, so the customer isn't surprised by capabilities they didn't intend to grant.

ApproachBenefitTrade-off
Use existing permission model (Community Admin, Moderator, Member)Works with current backend — minimal engineering effort; covers Approval authority is tied to roles that also carry other capabilities (e.g. Moderator can also moderate content), which may be broader than a customer wants for “just approve joins”

Out of Scope

ItemWhy it's out of scope / Assumptions
Setting up permissionSetting-up permission will be under the settings in the new destination page
Group discovery and search improvementsThis MVP covers list-level filtering and keyword search only. Suggested groups, recommendations — is a separate initiative.
Comments and Reactions won’t have their own entries under groupWe’re keeping Comments and Reactions out of scope. Under Content, we’ll surface Posts, Stories, Livestreams, and Polls as the main content types. Comments and Reactions are tied to that parent content rather than being standalone content types.Admins can still see the number of Comments and Reactions directly from the parent content. If they need to view the actual Comments or Reactions and manage them, they can click Manage Content to access the full details. Because of this, we don’t think separate entries for Comments and Reactions are necessary at this stage.
Edit CategoryWe scoped out the edit category because, given the time we have, it doesn’t add much value. If needed, they can still edit it or create a new one.
Deferred Scope

Membership-only groups are supported. A group's only function can be membership and role status, with no content component (Posts, Comments, Reactions) attached at all — e.g. a class roster, a loyalty tier, a waitlist. Use case could be : A customer creates a "Gold Members" group with no Posts, Comments, or Reactions attached. Users join or get added, the customer checks group membership to unlock a discount elsewhere in their app — the group itself never shows any content.		Currently, we can’t distinguish between them; it will require more effort, so we need to do it in a later scope.

User Stories / Journeys-IN PROGRESS

1. Manage the group list

As an admin, I want to view, filter, and search all groups on my network so that I can find and manage the ones I need.

  • Active groups are listed
  • Each listed group shows its post count
  • The active list can be filtered by category
  • The active list can be searched by group name
  • Deleted groups appear in a separate Deleted list — soft-deleted, not purged, so it stays available as a historical record
  • From the list, an admin can open Manage Activities ( Content, Manage Members, and Group Details) ( The final naming TBC with designers)
  • From the list, an admin can copy the group's ID (TBC with designer where to take this action)
  • From the list, an admin can copy the group's shareable link (TBC with designer where to take this action)
  • From the list, an admin can delete the group ((TBC with designer where to take this action)

2. Create a group

As an admin, I want to create a group with its own identity and access rules so that I can stand up a new space for a specific audience or purpose.

  • Customers can set the group's name
  • Customers can set the group's description
  • Customers can set the group's avatar
  • Customers can set the group's visibility: Public, Invite-only, or Discoverable & hidden
  • Customers can set the membership management mode: Anyone can join, Invite only, or Requires approval
  • Customers can set the push notification mode: Default (members get notifications but can turn them off), Silent (no notifications for anyone; members can't turn them on), or Subscribe (off by default; members can opt in)
  • Customers can assign the group to one or more existing categories
  • Customers can create a new category for the group
  • The group creator is automatically added as the group's first member, with the Owner role

3. Manage group categories

As an admin, I want to organize groups into categories so that I can keep a large number of groups manageable.

  • Admins can add a category
    • Name
    • Avatar
  • Admins can delete a category
  • The category list reflects active groups only
  • Deleting a category removes it from the category list without deleting the groups in it
  • Categories are shared across every group on the network — changes here affect the category picker everywhere

4. View group activity

As an admin, I want to see the content activity happening inside a group so that I can review what's being posted without leaving the group context.

  • Content is organized into five status tabs: Published, Featured, Scheduled, Requires approval, and Deleted
  • Activity can be searched by keyword
  • Activity can be filtered by creator
  • Activity can be filtered by timeframe
  • Activity can be sorted by creation date
  • Posts attached to the group are shown, with an action that redirects into the Post's own content management
  • This view surfaces content for reviewing, not configuring — it doesn't change how Posts, behave
  • Each activity item shows its author, including a verified badge when applicable
  • Each activity item shows its creation timestamp
  • Each activity item shows an image grid when the content includes images
  • Each activity item shows its reaction count
  • Each activity item shows its comment count
  • Each activity item has a "Manage content" action that redirects into that content's own management surface

5. Manage group members

As an admin or moderator, I want to manage who is in a group and what role they hold so that I can keep membership accurate and control access.

  • Members can be filtered by role
  • Role filtering applies only within the Active members view
  • Members can be viewed as all members
  • Admins can ban a member
  • Admins can remove a member
  • Admins can change a member's role
  • The Owner role cannot be banned, removed, or have its role changed
  • Banned members are shown separately, with an option to unban
  • Removed members are not shown at all
  • The members table shows: user, role, last activity, date joined, and available actions
  • Each status view (Active, Banned) shows a count of members in that status
  • Membership is a real view on the group itself, not a redirect into another component's data
  • Admin can add members and select multiple members

6. Manage sent invitations

As an admin, I want to track sent invitations, so that I can see who still needs to respond

  • Sent invitations can be filtered by status: All, Pending, or Declined
    • By default, it's filtered by Pending
  • Declined invitations can be resent
  • The invitations table shows: user, status, sent date, and available actions
  • Can add member from this view
    • Can select multiple members

7-Manage join requests

As an admin, I want to review and act on incoming join requests, so that I can control who joins request-based groups.

  • Pending join requests can be accepted
  • Admins can decline a pending join request
  • The join-requests table shows: user, requested date, and available actions
  • Admins can add a member directly from this view
    • Can select multiple members

8- Edit group details

As an admin, I want to view and edit a group's details, so that I can keep the group's information accurate as it evolves.

  • The form shows: group name, description, avatar, category, visibility, membership (requires moderator approval), and push notification setting
  • Category is a free-text field — admins can search existing categories or create a new one inline
  • Visibility options are: Public, Private & Visible, or Private & Hidden
  • Push notification setting has three modes: Default, Silent, or Subscribe
  • Saving updates the group with the new values
  • Admins can cancel out of changes without saving them
  • Admins can delete the group from this view — this moves it to the Deleted list and members can’t access it anymore

Open Questions

  • Is the notification a separate module that needs to be purchased separately?
    • If so, how should we handle invitations? Specifically, how will users accept or decline an invitation if the notification tray is the only place where we currently surface them?
    • FYI-We also have an Invitation API that clients can use to fetch invitations and display them in their own app notification tray. In this case, the client would be responsible for implementing the invitation experience on their side.

Decision
Notifications will be scoped to group notifications for now (similar to our product today). There’s too many edge cases to handle to open this up to non-group destinations at the moment unfortunately, but it’s something i’d like us to tackle next year.

What about user profile

User profiles, that's still in scope for phase 1. the only thing that i'm aware of, and that i agree on, is that brand profiles would be a paid component. Regular user profiles would also be like notifications, where you 'get' them without additional cost.

What should be under fundmental user module or other capabilities under user module?

Should we establish whether there should be a boundary between the fundamental user module and certain user-related capabilities that could potentially be gated/packaged separately (e.g. following another user, “friend feed”).
I think the key question is how we envision customers using and thinking about these capabilities, and whether that suggests they belong in the fundamental User module or should be independently configurable/packaged

As part of the users, the undestanding is that:

  1. The user module itself, such as sessions, user information, and users in the network list, is the fundamental part.
  1. Branded profiles, sponsored profiles, etc., are potential paid modules or features.
  1. User relationships, such as followingship and blocking users, are still unclear.
